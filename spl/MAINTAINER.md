# Splunk SPL Writer 인수인계

작성 기준: 2026-11-04, Asia/Seoul.

현재 상태는 **필드 추출 단계까지 구현한 프리뷰**다. 다음 컴퓨터의 새 세션에서는 사용자와 인터뷰를 이어가며 **CIM 정규화 단계**를 구현한다. 현재 패키지를 CIM까지 완성된 정식 버전으로 설명하지 않는다.

## 다음 세션에서 시작하기

원격 저장소는 `https://github.com/dollce/skills`, 기본 브랜치는 `master`다. 이 문서와 아래 파일을 읽고 이어서 작업한다. 표의 경로는 이 문서가 있는 `spl/` 디렉터리를 기준으로 한다.

| 파일 | 역할 |
| --- | --- |
| `splunk-spl-writer/SKILL.md` | 합의된 실행 흐름, 트리거, 최종 SPL 출력 형식 |
| `splunk-spl-writer/references/field-extraction.md` | 필드 의존 관계, 검색 비용, 배열 처리 지침 |

새 세션에 전달할 시작 요청:

```text
spl/MAINTAINER.md와 연결된 스킬 파일을 읽고 Skill Creator로 작업을 이어가줘.
다음 작업은 CIM 정규화 단계야. 로그 유형과 사용자의 목적에 맞춰
Endpoint, Network 등 적절한 CIM 카테고리를 선택하고 필요한 필드만 정규화해.
세부 규칙은 나와 인터뷰하면서 정해줘. 기존 탐색·샘플·파싱 흐름과
매크로 재사용을 위한 SPL 블록 형식을 보존해줘.
최종 SPL은 사용자나 다른 에이전트에게 제공하는 것이 목적이야.
최종 SPL 실행, 성능 비교 실험, 매크로 등록은 이 작업에 포함하지 마.
```

## 확정된 목적과 범위

- `SPL 생성`, `SPL 작성`, `SPL 만들어줘`, Splunk 검색 쿼리 작성 요청에 자동 선택되는 스킬이다. 이름은 `splunk-spl-writer`, `allow_implicit_invocation`은 `true`다.
- 실제 데이터 구조를 근거로 사용자의 **처음 요청에 가장 적절한 최종 SPL을 생성하여 제공**한다. 수신자는 사용자 또는 다른 에이전트다.
- 에이전트는 연결된 `splunk-mcp`로 검색 대상 탐색과 실제 이벤트 샘플 조회를 직접 수행한다. 최종 SPL을 실행해 검증하거나 벤치마크하는 흐름은 사용자가 명시적으로 제외했다.
- 상세 워크플로우는 인터뷰로 정한다. 조사 노트의 모든 권고를 사용자 요구사항으로 승격하거나, 미결정 매핑·예외 정책을 임의로 추가하지 않는다.

## 구현된 흐름

### 검색 대상 탐색

가장 먼저 수행할 쿼리는 다음과 같다. `keyword`를 질문에 적절한 Splunk 토큰으로 바꿔 `splunk-mcp`에서 실행한다.

```spl
| tstats count where index=* TERM(keyword) by index, sourcetype
```

실제 반환된 `index`·`sourcetype` 조합 중 질문에 적절한 검색 대상을 선택한다. 여러 조합을 사용할 때는 조합을 보존한다. 인덱스와 sourcetype을 독립적으로 OR로 묶어 불필요한 교차 조합을 검색하지 않는다.

### 실제 이벤트 샘플 확인

선택한 조합에서 필드명·값·로그 구조를 알아낼 만큼만 직접 조회한다. 목적에 맞는 짧은 시간, 관련 조건, 작은 반환 건수를 함께 지정한다. `_raw`와 추출 필드를 함께 확인하고, 확보한 샘플을 재사용한다. 필요한 구조가 확인되면 추가 조회를 멈춘다.

검색량과 호출 횟수를 함께 줄인다. MCP rate limiting은 서버가 설정한 구간의 전체·도구별 호출 횟수에 적용되므로 소수의 결과만 반환한다고 제한을 피할 수 있는 것은 아니다. 병렬·중복 조회를 피하고, 제한 응답 시 즉시 반복 재시도하지 않는다. 실제 서버가 제공한 재시도 안내가 없으면 임의의 대기 시간을 만들지 않는다. 세부 사항은 스킬 본문과 연결된 공식 문서를 따른다.

### 필요한 필드 추출·유지

사용자가 말한 **1번 단계**다. 다음 사항은 이미 반영했다.

- 검색 범위 축소와 후속 필드 처리량 축소를 구분한다. `fields`는 버킷에서 특정 열만 읽는 파서가 아니다.
- 후속 필터·출력·정규화·예외 처리에 필요한 입력을 유지하고, 확인된 기존 필드는 재사용한다.
- 필터용 최소 추출·계산 → 필터 → 나머지 추출을 의미가 유지되는 범위에서 적용한다. 필요에 따라 `fields`, `spath`, `rex`, `eval`, 다중값 함수를 선택한다.
- 배열 원소별 행이 필요할 때만 `mvexpand`를 사용한다. 객체 안의 필드 관계와 원본 이벤트/배열 원소라는 행 단위를 보존한다.
- 큰 원문·중간 필드는 마지막 사용 후 제거한다. 원문이 최종 증거로 필요하면 유지한다. 형변환 실패만으로 요청에 없는 이벤트 제외 조건을 추가하지 않는다.
- 재사용할 파싱 블록은 `fields`로 출력 필드를 정리한다. 표시용 `table`을 이 블록에 넣지 않는다.
- 샘플의 짧은 시간 범위·`head`·반환 건수 제한을 최종 SPL에 복사하지 않는다. 최종 범위는 원래 요청을 따른다.

## 다음 작업: CIM 정규화

사용자가 말한 **2번 단계**다. 스킬 전체의 두 번째 단계인 샘플 조회와 혼동하지 않는다. 이번 인수인계 시점에는 **출력 블록 경계만 존재하며, CIM 선택·매핑 워크플로우는 아직 구현하지 않았다.**

이번에 확정된 다음 요구사항:

1. 로그 유형과 사용자의 목적을 함께 고려하여 Endpoint, Network 등 적절한 CIM 카테고리를 선택한다.
2. 해당 use case에 필요한 필드만 정규화한다. 카테고리의 모든 필드를 일괄 생성하지 않는다.
3. 필드 파싱 블록의 실제 출력을 입력으로 사용하며, CIM 정규화는 별도 블록으로 제공한다.

다음 세션에서 인터뷰·자료 확인으로 결정할 사항:

- 사용자 표현인 카테고리를 실제 CIM 모델·데이터셋과 어떻게 연결할지. 선택할 공식 CIM 문서와 대상 버전을 확인한다.
- 여러 범주가 관련될 때 목적별 선택·분리 기준, 단일 결과에 필요한 최소 필드 집합.
- 원본 필드의 의미와 CIM 필드의 의미가 일치하는지, 단순 이름 변경과 값·자료형·단위 변환의 구분.
- 소스별 필드 우선순위, 서로 다른 action 표현, 방향성이 있는 주소·장비 필드, 누락·미매핑 값의 처리.
- 일반 SPL의 필요한 필드 정규화와 전체 CIM 호환성 검증의 경계. 이름만 바꿨다는 이유로 완전한 CIM 호환을 주장하지 않도록 설계한다.
- 정규화 값에 의존하는 필터와 예외 처리의 위치. 파싱 단계에 넣는 조기 필터가 결과 의미를 바꾸지 않는지 확인한다.

위 항목은 **아직 합의하지 않은 설계 질문**이며 확정된 매핑 규칙이 아니다. 사용자 노트의 CIM 관련 예시를 출발점으로 삼고, 관련 공식 모델 문서만 선택해 확인한다. 환경에 없는 필드·lookup·태그·매크로를 만들어서 존재하는 것처럼 사용하지 않는다.

권장 편집 위치는 `SKILL.md`의 필드 추출 단계 다음이다. 상세 카테고리·매핑 지침이 충분히 커지면 `references/`에 분리하고 본문에서 필요한 시점에만 읽도록 연결한다. 기존 파싱 지침을 복제하지 않는다. 예외 처리 상세 정책은 별도 미완료 항목이다.

## 최종 결과의 형식

실제 SPL을 **하나의 코드 블록**으로 제공하고 아래 논리 블록을 순서대로 구분한다.

1. 검색 범위 + 필요한 필드 파싱·유지
2. CIM 정규화
3. 예외 처리

블록 사이에 **연속 개행 두 개(`\n\n`, 빈 줄 한 줄)**를 넣는다. 필요한 분석·집계는 입력이 준비된 뒤 별도 블록으로 연결한다. 현재 문서의 개행 해석을 바꾸려면 사용자 의도를 확인한다.

블록을 나중에 매크로로 옮길 수 있도록 입출력 필드와 행 단위를 명확히 한다. 임의의 매크로 이름·호출문·정의를 만들거나 Splunk에 등록하지 않는다. 미정인 CIM·예외 규칙을 가짜 코드로 채우지 않는다. 역할 설명은 코드 밖에 둔다.

## 검증 기록과 한계

- Skill Creator의 `quick_validate.py`를 사용한 형식 검증을 통과했다. 내부 참조 파일과 UI 메타데이터도 확인했다.
- 이전 세션에서 독립 에이전트로 모의 요청을 점검했다. **실제 Splunk 실행 결과가 아니다.**

| 모의 사례 | 확인한 내용 |
| --- | --- |
| 기존 필드 + JSON payload의 결제 로그 | 검증된 소스 조합 유지, 기존 필드 재사용, 필요한 경로만 추출, 후속 `category_code` 보존, 요청한 전체 기간 유지 |
| 누락 키가 있는 객체 배열 | 원소별 IP·포트 관계 유지, 부모 필드 추출 재사용, 숫자 변환, 요청한 증거 원문 보존 |
| 반환값 없는 rate limit 오류 | 추가 조회 중단, 재시도 시각이나 조회 성공을 꾸며내지 않음 |

모의 점검 중 불필요한 `where isnum(...)`가 행을 제거하는 문제와 파싱 블록에 `table`을 넣는 문제가 드러나 지침을 보강했다. 새 모의 요청에서 행 보존과 `fields` 출력 구성을 확인했다. 대화 기반 점검이며 저장된 자동 테스트 스위트는 아니다.

실제 `splunk-mcp` 연결, 운영 로그 조회, 최종 SPL의 정확성·성능, 설치 후 자동 트리거 동작은 검증하지 않았다. 다음 세션의 CIM 점검도 먼저 모의 샘플로 범위·매핑·출력 의미를 확인한다. 참고 노트의 A/B 성능 실험 절차를 실행 승인으로 해석하지 않는다.

배포 준비 과정에서 두 ZIP의 체크섬·내부 경로·파일 포함 범위를 확인했다. 이 컴퓨터의 임시 경로에 handoff ZIP을 풀어 원본 파일과 비교하고, 다른 작업 디렉터리에서 재빌드하여 두 ZIP과 체크섬 파일이 바이트 단위로 동일한 것을 확인했다. 압축 해제본의 내부 참조와 스킬 형식 검증도 통과했다. 이는 로컬 이동·재빌드 검증이며 다른 운영체제나 대상 컴퓨터의 설치 검증은 아니다.

## 배포 준비와 다른 컴퓨터로 이동

배포 원본은 공개 GitHub 저장소 `dollce/skills`이며 기존 저장소의 MIT 라이선스를 따른다. 설치 이름은 `splunk-spl-writer`, 설치 대상 디렉터리는 `spl/splunk-spl-writer/`다. 루트 `skills.sh.json`의 `paths: ["./spl"]`로 CLI 검색 위치를 등록한다. `spl/SKILL.md`나 별도 복사본을 만들어 하위 스킬을 가리거나 중복 발견되게 하지 않는다.

일반 사용자는 다음 명령으로 설치한다. 기본은 프로젝트 범위이며 전역 설치에는 `--global`을 붙인다. 자세한 설치·업데이트·삭제 방법은 [README.md](README.md)를 따른다. 설치 기록을 보존하고, 스킬 이름과 경로를 바꾸면 기존 설치의 업데이트에 미치는 영향을 검토한다.

```sh
npx skills add https://github.com/dollce/skills --skill splunk-spl-writer
```

`npx skills`는 이 GitHub 원본을 추적한다. 별도 npm 게시나 매크로·Splunk 배포는 필요하지 않다. 스킬 변경은 PR로 검토하여 `master`에 반영한다. 현재 버전은 계속 CIM 상세 단계가 없는 프리뷰이며, 저장소 게시가 운영 환경에서의 SPL 검증을 뜻하지 않는다.

저장소 루트에서 Python 3으로 실행한다. 빌드 스크립트는 표준 라이브러리만 사용한다.

```sh
python3 spl/scripts/build_release.py
```

| 산출물 | 용도 |
| --- | --- |
| `dist/splunk-spl-writer-preview.zip` | 현재 스킬 폴더만 포함하는 설치용 프리뷰 |
| `dist/splunk-spl-writer-handoff.zip` | 이 문서, 조사 노트, 스킬, 빌드 스크립트를 포함하는 개발 인수인계본 |
| `dist/SHA256SUMS` | 두 ZIP의 SHA-256 체크섬 |

표의 `dist/`는 `spl/dist/`이며 생성물은 Git에서 제외한다. **다음 컴퓨터의 개발 세션에는 Git clone을 우선 사용한다.**

```sh
git clone https://github.com/dollce/skills.git
cd skills
```

새 세션에서 `spl/MAINTAINER.md`를 읽는다. 수동 이동이 필요하면 handoff ZIP과 체크섬 파일을 가져와 새 폴더에 풀고 `spl/MAINTAINER.md`를 읽는다. ZIP은 `spl/` 작업 자료만 포함하며 `.git`, 루트 CLI 검색 설정·CI, 대화 기록, 로컬 계정 설정이나 MCP 인증 정보는 포함하지 않는다. handoff를 독립적으로 재빌드하려면 압축을 푼 상위 폴더에서 위 빌드 명령을 실행한다.

패키지에는 `splunk-mcp` 서버나 연결 설정이 포함되지 않는다. 대상 컴퓨터에서 사용자가 연결한 도구의 검색 스키마·권한을 확인해야 한다. 도구가 없을 때 결과를 꾸며내거나 설치 파일이 자동으로 Splunk 연결을 구성한다고 설명하지 않는다.

CLI로 관리할 설치는 GitHub URL을 사용한다. 수동 ZIP 복사는 CLI의 원격 업데이트 추적 설치와 다르다. 개발용 handoff 폴더 전체를 스킬로 설치하지 않는다. 설치 후 `npx skills list`로 확인하고 Codex에 변경이 보이지 않을 때 재시작한다. [OpenAI 공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills)

## 이후 변경의 검증·전달

스킬을 수정하면 저장소 루트에서 아래 검증을 수행한다. Python 가상환경 사용 방법은 README를 참고한다.

```sh
python3 -m pip install -r spl/requirements-dev.txt
python3 spl/scripts/check_release.py
npx --yes skills@1.7.6 add . --list
```

루트 `.github/workflows/validate-spl.yml`에서 같은 검증을 수행한다. Skill Creator의 `quick_validate.py`가 있는 환경에서는 그 검증도 추가할 수 있지만, 특정 컴퓨터의 절대 경로에 의존하지 않는다. 관련 모의 요청으로 동작을 확인하고 필요하면 패키지를 다시 생성한다. CLI 로컬 경로 설치 점검은 원격 업데이트 점검과 구분한다. GitHub 설치는 설치 기록의 원본·스킬 경로를 확인하고 `check`·`update`에 `--project` 또는 `--global`을 명시한다.

빌드는 파일 누락과 패키지 구조를 확인하는 도구이며 스킬의 행동이나 SPL 의미를 검증하는 도구가 아니다. 압축 해제본에서도 참조 경로가 유효하고 원본과 동일한지 확인한다. 내용이 바뀌면 ZIP과 체크섬을 함께 갱신한다.

개발 PR을 만들게 되면 사용자의 기존 전달 선호를 적용한다. `pr-delivery` 스킬과 전용 `pr_delivery` 에이전트를 사용하고, 리뷰는 매번 이력 없는 새 에이전트(`fork_turns="none"`)에서 시작한다. PR 식별자·체크아웃·원래 요구사항·현재 권한만 전달하며, 작성자 설명·이전 지적·주장한 테스트 결과를 넘기지 않는다. 변경 후에는 새 리뷰어로 다시 검토하고, 독립 리뷰와 필수 검사가 통과하면 이미 허용된 범위에서 병합한다. 이 선호는 Splunk 운영 변경, 최종 쿼리 실행, 실험 환경 구축 또는 데이터 주입을 허용하지 않는다.
