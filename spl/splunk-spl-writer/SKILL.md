# Splunk SPL Writer

사용자의 처음 요청과 실제 로그 구조에 맞는 최적화된 SPL을 만들어 사용자 또는 다른 에이전트에게 제공한다. 완료 조건은 최종 SPL 제공이다. `splunk-mcp`는 검색 대상과 실제 로그 구조를 파악하는 데 사용하며, 생성한 최종 SPL의 실행·성능 비교 실험은 이 워크플로우에 포함하지 않는다.

## 첫 단계: 검색 대상 index와 sourcetype 파악

SPL 작성 요청을 받으면 가장 먼저 다음 탐색 쿼리로 관련 토큰이 존재하는 `index`와 `sourcetype`을 확인한다.

```spl
| tstats count where index=* TERM(keyword) by index, sourcetype
```

`keyword`를 사용자 질문의 검색 목적에 적절한 Splunk 토큰으로 바꾼다.

연결된 `splunk-mcp` 도구로 에이전트가 이 탐색 쿼리를 직접 실행하고 반환된 결과를 확인한다. 실행 결과에 나타난 `index`와 `sourcetype` 조합을 근거로 질문에 가장 적절한 검색 대상을 선택하고, 후속 SPL 작성에 반영한다.

## 두 번째 단계: 실제 이벤트의 필드와 로그 구조 확인

선택한 `index`·`sourcetype`에서 실제 이벤트 샘플을 조회한다. 이 쿼리도 에이전트가 `splunk-mcp`로 직접 실행한다. 목적은 해당 use case의 SPL을 작성하는 데 필요한 **실제 필드명, 필드값, 로그 구조**를 확인하는 것이다.

- 샘플 검색은 선택한 `index`·`sourcetype` 조합으로 한정한다. 해당 use case와 관련된 토큰 및 이미 확인한 조건으로 검색 시작 단계부터 범위를 좁힌다.
- 사용자 요청의 기간이나 사건 발생 시각 안에서 목적에 맞는 가장 짧은 시간 범위를 명시한다. 기간이 없으면 짧은 탐색 구간을 선택하고 그 범위를 밝힌다. 전체 기간이나 넓은 기본 검색 범위에 맡기지 않는다.
- 구조 파악에 필요한 소수의 이벤트만 반환하도록 작은 양의 건수 제한을 명시한다. `head`와 도구가 실제로 지원하는 반환 건수 옵션을 활용하되, 반환 건수 제한만으로 검색 범위까지 좁아졌다고 판단하지 않는다.
- 작은 샘플에서 `_raw`와 실제 추출 필드·값을 함께 확인한다. 필요한 중첩 구조, 배열, 값 형식 등을 확인할 수 있도록 하며, 필드 존재를 추측해 필요한 데이터를 미리 제거하지 않는다. 반환 데이터가 생략되거나 잘렸다면 확인하지 못한 구조를 구분한다.
- 확보한 샘플을 재사용하고 필요한 필드·값·구조를 확인하면 조회를 멈춘다. 추가 조회는 아직 확인하지 못한 항목이 있을 때만 그 항목을 확인할 작은 범위로 수행한다. 빈 결과만으로 데이터나 필드가 없다고 단정하거나 검색 범위·건수를 무작정 확대하지 않는다.

시간·조건·반환량을 함께 줄이는 근거는 [Splunk 검색 최적화 지침](https://help.splunk.com/en/splunk-enterprise/search/search-manual/9.0/optimizing-searches/quick-tips-for-optimization)을 참고한다.

## 세 번째 단계: 필요한 필드 추출·유지 설계

검색 대상과 로그 구조를 파악하면 사용자의 처음 요청으로 돌아가 필요한 결과와 행의 단위를 정한다. 필드 추출을 설계할 때 [필드 추출·검색 비용 지침](references/field-extraction.md)을 읽고, 확인한 필드·값·구조에 맞춰 최종 SPL을 작성한다.

- 검색 시작 부분에서 선택한 `index`·`sourcetype` 조합과 사용자가 요청한 시간·조건을 적용한다. 여러 소스는 실제 조합을 보존하여 OR로 연결한다. 인덱스 목록과 sourcetype 목록을 각각 OR로 묶어 의도하지 않은 교차 조합을 포함하지 않는다.
- 최종 출력, 필터, 집계 및 후속 정규화·예외 처리에 필요한 입력 필드를 역으로 확인한다. `fields`로 필요한 입력을 일찍 유지하되, 아직 사용하지 않은 원문·중간 필드를 제거하지 않는다.
- 이미 정확하게 추출된 필드는 재사용한다. 추가로 필요한 값에만 `spath`, `rex`, `eval` 등을 적용한다. 필터에 필요한 최소 추출·계산을 먼저 수행하고, 조건을 통과한 이벤트에 나머지 추출을 적용한다. 모든 명령을 일괄 삽입하는 고정 템플릿으로 만들지 않는다.
- 다중값은 결과 단위에 맞게 처리한다. 배열 원소별 행이 필요할 때만 `mvexpand`를 사용하고, 같은 객체의 필드 관계를 보존한다. 원문과 큰 중간 필드는 마지막 사용 직후 제거한다.
- 파싱 블록 끝에는 `fields`로 후속 블록에 필요한 필드만 남긴다. 표시용 `table`은 이 재사용 블록에 넣지 않는다. 필드명·의미와 행 단위가 명확하여 이 블록을 나중에 매크로로 재사용할 수 있어야 한다.

샘플 탐색용 짧은 시간 범위, `head`, 반환 건수 제한을 최종 SPL에 그대로 옮기지 않는다. 최종 쿼리의 범위와 결과 개수는 원래 요청을 따른다. 최적화 때문에 이벤트 범위, NULL 처리, 객체 간 관계 또는 집계 단위를 바꾸지 않는다.

## 최종 SPL 제공 형식

매크로로 옮겨 재사용하기 쉽도록 **실제 SPL 본문을 하나의 코드 블록**으로 제공한다. 다음 논리 블록 사이에는 연속된 개행 두 개를 넣어 빈 줄로 구분한다.

1. 검색 범위(`index`·`sourcetype` 등) + 필요한 필드 파싱·유지
2. CIM 정규화: Endpoint, Network 등 해당 범주에 맞는 정규화
3. 예외 처리: 해당 요청에 적용할 예외 조건·목록

사용자가 요청한 분석·집계가 있으면 해당 입력 필드가 준비된 뒤 별도 블록으로 연결한다. 각 블록은 앞 블록이 남긴 필드를 입력으로 사용하고, 전체를 연결했을 때 SPL 문법과 데이터 의존 관계가 유지되어야 한다.

파싱, CIM 정규화, 예외 처리를 뒤섞지 않는다. 정규화나 예외 처리의 구체 규칙이 주어지지 않은 단계는 임의의 매핑·예외 목록으로 채우지 않는다. 실제로 필요한 블록만 포함하며, 역할과 입출력 필드에 대한 짧은 설명은 코드 블록 밖에 둔다.

임의의 매크로 이름·호출문·정의를 만들거나 Splunk에 등록하지 않는다. 블록 구분을 위해 SPL 코드 안에 설명용 가짜 명령이나 자리표시자를 넣지 않는다. 최종 SPL을 실행·검증했다거나 성능 개선을 측정했다고 표현하지 않는다.

## splunk-mcp 호출 절제

탐색과 샘플 조회 모두 검색량뿐 아니라 도구 호출 횟수를 최소화한다. [MCP Server 2.1 rate limiting 문서](https://help.splunk.com/en/splunk-cloud-platform/mcp-server-for-splunk-platform/2.1/monitor-and-administer-splunk-mcp-server/mcp-server-rate-limiting)에 따르면 제한은 설정된 시간 구간의 전체 도구 호출 수와 개별 도구 호출 수에 적용된다. 작은 결과를 반환하는 것만으로 rate limiting을 피할 수 있다고 가정하지 않는다.

- 이전 결과를 확인한 뒤 필요한 다음 조회를 순차 실행한다. 후보별·필드별 병렬 조회, 동일 검색의 반복 실행, 불필요한 상태 확인 호출을 피한다.
- 확인 가능한 서버의 호출 한도와 시간 구간을 따른다. 한도가 공개되지 않았다면 임의의 기본 호출 횟수나 대기 시간을 가정하지 않는다.
- 제한 응답을 받으면 추가 호출을 멈추고 실제 반환된 재시도·초기화 시각 안내가 있으면 따른다. 안내가 없으면 제한 상황과 미확인 항목을 알린다. 즉시 반복 재시도하거나 도구·노드를 바꿔 제한을 우회하지 않는다.
